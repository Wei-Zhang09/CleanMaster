# ADR-002：自动更新采用双源（Gitee 优先、GitHub 兜底）

- 状态：已接受（2026-11-06）
- 相关：`Services/UpdateService.cs`、`AGENTS.md`（发布流程）、`HANDOVER.md`（第二轮）

## 背景

自动更新原先只查 GitHub Releases。用户在国内、无代理的环境下实测反馈"更新不可用"，两个独立问题：

1. **下载链路在国境内是断的**。不走代理实测：`api.github.com` 三次请求均 200（约 0.85 s）；安装包直链 302 到
   `release-assets.githubusercontent.com` 后返回 206 但**实际传输 0 字节**，2.9–11 s 后超时；发布页 HTML 6.7 s 可达。
   即：元数据能取到，资产取不到。
2. **失败被吞成"已是最新"**。`CheckForUpdateAsync` 捕获异常返回 `null`，ViewModel 对 `null` 一律显示
   "已是最新版本"，用户无法区分"网络不通"和"确实没有新版本"。

## 备选方案

- **A. 只把失败变可见**：提示"检查更新失败"并给发布页链接。改动最小，但用户仍要手动下载安装包，等于放弃自动更新。
- **B. 加第三方镜像**：依赖不受控的第三方，安装包来源不可验证，安全上不可接受。
- **C. 双源托管（选中）**：在国内可直连的 Gitee 同步发布同一版本，客户端优先走 Gitee。

## 事实核对

1. Gitee OpenAPI v5 `GET /repos/{owner}/{repo}/releases/latest` 对**公开仓库免 token**，实测 200 / 0.3–0.6 s。
2. Gitee 资产直链实测 **45 MB / 22 s ≈ 2.04 MB/s**，下载完成且 SHA256 与本地构建一致。
3. 两端字段差异：Gitee 的 `tag_name` 不带 `v`（`3.4.2`）、`assets` **没有 `size`、没有 `digest`**；
   GitHub 两者都有。
4. 由此产生的校验缺口：Gitee 无法用 digest 校验，只能把 SHA256 写进发布说明，由客户端解析。

## 决策

1. 更新源两个：**Gitee 优先、GitHub 兜底**，任一可用即可完成更新。
2. **按优先级取第一个可用源，而不是取版本最高者**。
3. Gitee 缺失 digest 时，从发布说明解析 `SHA256: <64 位>` 校验；缺失则跳过校验并记日志，不阻断更新。
4. 全源失败抛 `UpdateCheckException`，界面区分"网络失败"与"无更新"，失败提供「打开发布页」。

## 理由

- **选源优先级而非版本最高**：反例是 GitHub 有 3.4.2、Gitee 只有 3.4.1。若按版本取高会选中 GitHub，
  国内用户下载必挂——明明 Gitee 上有可用版本却更新失败。可达性优先于版本新鲜度。
- **不阻断缺 digest 的情况**：Gitee 发布说明是人工填写的，写漏不应让整条更新链路失效；
  校验是加分项，不是前置条件。
- **不引第三方镜像**：安装包是本机以管理员权限执行的程序，来源必须是我们控制的账号。

## 后果

- **每次发版必须发两处**：GitHub（CI 自动出包）与 Gitee（手工传包 + 说明里写 SHA256）。
  漏发 Gitee 的后果是"国内用户看不到更新"，且因为优先级逻辑不会自动回落（Gitee 无更新时才回落 GitHub），
  这一条已写进 `AGENTS.md` 的发布流程。
- 两个源的安装包允许字节不同（不同机器/不同 Inno 版本构建），因此 **SHA256 必须对应各自上传的那个文件**。
- Gitee 上传有约 20 s 的可见延迟，发布后立即查 API 可能看不到资产，不应据此判定失败。
- 若以后发版频繁，可考虑在 CI 中用 Gitee OpenAPI + token 自动建 Release（token 不得入库）。
